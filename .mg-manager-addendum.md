## Addendum 23 (owner): CLOUD SAVE — straightforward, no account required
A career must survive a lost phone, a cleared browser and a device switch.
Constraint: the game ships as static files with NO backend of its own, so
"cloud" must not mean "trust a server we do not run with a child's data".
The design:
- SAVE CODE (primary, works everywhere): one button turns a career into a
  compact, compressed, checksummed text code the owner can put anywhere he
  already trusts — Notes, a text to himself, iCloud. Another button restores
  from a pasted code. Round-trip must be lossless and version-migrating.
- FILE EXPORT / IMPORT: download the save as a .json / .gsave file and load
  it back; on iOS this lands in Files/iCloud Drive, which IS his cloud, with
  no third party involved.
- AUTO-BACKUP: keep the last N autosaves per slot locally with timestamps and
  a one-tap restore, so a corrupt save is never fatal.
- If a real sync backend is ever added it must be opt-in, explained plainly,
  and never required to play.
The UI lives on the save-slot screen: Save code / Restore / Export / Import /
Backups, each one tap, each with a plain-English confirmation.

## Addendum 24 (owner): ONE SET OF SAVES, EVERYWHERE — 10+ accounts
THE PROBLEM (owner, correctly): browser storage is per-origin AND per-device,
so the artifact page, http://127.0.0.1:8000 and mobile each keep SEPARATE
saves that silently diverge. Ten careers must not become thirty.

THE ARCHITECTURE:
- ONE CANONICAL HOME: the published artifact. It declares the `artifact`
  runtime capability, so the page can write state back into ITSELF via
  claude.use('artifact').publish(html) — account-bound storage that every
  device opening that link shares. This is the only cross-device store
  available without standing up a server, and it needs no login beyond the
  owner's own Claude account.
- LOCAL PLAY STAYS INSTANT: every action autosaves to localStorage
  immediately (no publish, no reload). Publishing happens only on a
  deliberate "Sync saves" action, because publish() reloads every open view —
  the UI must say so before it does it.
- MERGE, NEVER CLOBBER: each slot carries a monotonic revision + device id +
  timestamp. On load, embedded cloud slots merge with local by revision;
  a genuine conflict shows both and lets the owner pick, never silently
  overwrites. publish() 'conflict' is routine: reload and re-merge, no retry.
- 10+ SLOTS, and a slot list that shows where each save came from and when it
  last synced, so divergence is visible instead of surprising.
- THE LOCAL SHOP (127.0.0.1) is a secondary surface: it bridges by save code
  and .gsave file (addendum 23). The UI must name the surface you are on so
  it is never ambiguous which copy you are playing.
- Read-only viewers cannot publish: degrade to local-only with a plain note.

## Addendum 27 (measured): FILE SAVE MUST USE THE DOWNLOADS CAPABILITY
The artifact viewer never grants a page download permission, so the cloud-save
"export .gsave" feature — a plain blob link — silently does NOTHING for the
owner on the published URL. It must go through the runtime capability:
  const dl = await claude.use('downloads');   // null => hide the affordance
  await dl.save({ filename, data });          // viewer confirms; may decline
The page declares `downloads`. Keep a graceful fallback for the local server
copy (where a blob link does work). Save CODES (copy/paste text) remain the
primary path because they need no capability at all.
