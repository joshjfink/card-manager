## 0. AUTHORITY — what these addenda overturn

`.mg-manager-fm.md` §12 explicitly CUT transfers, loans, team talks and
half-time talks. Addenda 12, 13 and 14 are later owner words and therefore
**override §12 on those four items only**. Authority order is now:

> Addenda 12–17 › Addendum 2 › `.mg-manager-fm.md` › Addendum 1 › build spec

What survives from §12's reasoning, and is binding on every new system here:

- **No money-pressure copy.** Offers carry no timers, no countdowns, no
  "last chance", no red urgency. An offer that expires does so silently with
  one kind news line.
- **Never blocks.** No new screen may gate CONTINUE. Every decision card is
  skippable; skipping is always "not for sale / no thanks", never a penalty.
- **No fail states.** Rejecting a bid costs mood, never points, money or a
  sacking. No board confidence.
- **Family safety is structural.** Loans and trades never separate Gibson or
  Ellis from the club unless the manager explicitly does it, and the
  CPU never *asks* for them (family cards aren't chips).
- **Honesty markers stay.** The `not EA data` footer, demo-mode banner, and
  plain-English odds are untouched; every new number shown to the owner is a
  real derived number, never a fabricated flourish.

### The one law over the new systems

> **Only a tier change may change `effSkill`.**
> `effSkill(p) = 0.75·base + 0.25·PARS[tier].score` — exactly, forever.
> XP, levels, quests, mastery stars, coaches, loans, trades, morale, rivalry
> and team talks are all **forbidden** from touching `base`, `tier→score`, or
> the coefficient pair. Harness gate **G26** proves it every run.

Managerial verbs (talks / calls / grudge) act on the *team* multiplier table
inside `simulate`, never on a player's skill. That is the seam that keeps the
75/25 law and balance gates 1–8 intact while giving the owner real decisions.

## 2. SAVE MIGRATION — v2 → v3

### 2.1 The loader becomes a chain (do this first, alone, and ship it)

`loadSave()` today: `if (s && s.v === 2 && s.profiles) { SAVE = s; return; }` —
anything else is backed up and wiped. That is the promise-breaker addendum 8
names. Replace with:

```js
const SAVE_V = 3;
const SLOT_KEY = () => SAVE_KEY;          // ← addendum 17's slots land here, one line
const MIGRATIONS = { 2: up2to3 };         // v -> function(save) -> save at v+1

function loadSave() {
  let raw = null;
  try { raw = localStorage.getItem(SLOT_KEY()); } catch (e) {}
  if (raw) {
    let s = null;
    try { s = JSON.parse(raw); } catch (e) {}
    if (s && s.profiles && typeof s.v === 'number') {
      let ok = true;
      try {
        while (s.v < SAVE_V) {
          const up = MIGRATIONS[s.v];
          if (!up) { ok = false; break; }
          s = up(s);                       // must bump s.v itself
        }
      } catch (e) { ok = false; }
      if (ok && s.v === SAVE_V) {
        backup(raw, '-pre' + SAVE_V);      // keep the pre-migration blob once
        SAVE = s; return;
      }
    }
    backup(raw, '-bak');                   // unparseable, or from a FUTURE build
  }
  SAVE = { v: SAVE_V, createdAt: Date.now(), updatedAt: 0,
           activeProfile: 'p1', profiles: { p1: null, p2: null } };
}
```

Rules that make this safe and are gated:

1. A migration **only adds**. It never deletes, renames or reinterprets a v2
   field. Career code already ignores unknown fields (spec law), so a v3 build
   reading a v3 save written by a later build degrades instead of wiping.
2. A save from a **newer** build (`s.v > SAVE_V`) is backed up and a fresh
   career starts — but the backup key is `-bak` and the owner is told, in the
   BOOT copy, that the old career is kept. Never silent.
3. `-pre3` backup is written **once**, before the migrated save is first
   persisted. It is the undo.
4. Migration is **idempotent and pure**: running `up2to3` on an already-v3
   save is impossible (guarded by `s.v`), and running it twice on a clone
   yields deep-equal results. Gated by **G27**.

### 2.2 `up2to3(save)` — the exact delta

Per profile (`p1`, `p2`, skipping nulls):

```js
function up2to3(s) {
  for (const k of ['p1','p2']) {
    const p = s.profiles[k]; if (!p) continue;

    /* --- RPG core (addendum 15) --------------------------------------- */
    p.xp = {};                       // per PLAYER, cumulative, never reset
    for (const pid of Object.keys(p.apps || {}))
      p.xp[pid] = (p.apps[pid] || 0) * XP_PER_APP;      // XP_PER_APP = 100
    p.quests  = {};                  // pid -> [chainStep, progress]
    p.mastery = {};                  // pid -> 0..3 stars
    p.disc    = {};                  // pid -> % off next climb (quest reward)

    /* --- upgrade economy (addendum 14) -------------------------------- */
    p.coaches = [];                  // <=3 of 'climb'|'fitness'|'sharp'|'solid'
    p.plan    = [null, null, null];  // weekly training slots: {focus, pid}

    /* --- managerial verbs (addendum 14) ------------------------------- */
    p.tactics.talk     = 'steady';
    p.tactics.calls    = { lead: 'hold', level: 'hold', trail: 'hold' };
    p.tactics.penTaker = null;       // wires the engine field that already exists
    p.rivals  = {};                  // clubId -> grudge 0..3

    /* --- market verbs (addenda 12, 13) -------------------------------- */
    p.trades  = [];                  // inbound swap proposals
    p.loans   = [];                  // active + settling loan spells
    for (const o of (p.offers || [])) if (!o.kind) o.kind = 'sale';
    p.dynasty = { sales: [], loans: [], hof: [] };      // capped 5/5/12

    /* --- prefs -------------------------------------------------------- */
    p.settings = { autoCalls: false, reduceMotion: false };
    p.seen = p.seen || {};
  }
  s.v = 3;
  return s;
}
```

**The migration's load-bearing line is `p.xp[pid] = p.apps[pid] * 100`.**
XP gates are set at exactly `APP_GATES × 100` (below), so *every card that
could be trained in a v2 save can still be trained the instant v3 loads*. A
migration that made a five-season career suddenly ineligible would be a wipe
by another name. **G20d** asserts this over the v2 corpus.

### 2.3 Pruning and size

`saveNow()` prunes `energy≠100`, `form`, `bs`, `vd`, `apps`. Add:

```js
p.xp      = pruneMap(p.xp);                     // 0 dropped
p.mastery = pruneMap(p.mastery);
p.disc    = pruneMap(p.disc);
p.quests  = dropIf(p.quests, v => !v[0] && !v[1]);
p.rivals  = pruneMap(p.rivals);
p.plan    = p.plan.map(s => s || null);
p.dynasty.sales = p.dynasty.sales.slice(-5);    // caps, not history
p.dynasty.loans = p.dynasty.loans.slice(-5);
p.dynasty.hof   = p.dynasty.hof.slice(-12);
```

Budget: the FM doc's **<64 KB** gate stands. Worst realistic case adds
`xp` (≤980 keys × ~12 B ≈ 12 KB) and `quests` (≤980 × ~16 B ≈ 16 KB) on top
of `collection`. `quests` is the risk — cap it: **a quest entry is stored only
for cards that have STARTED a chain** (first qualifying match), and completed
chains collapse to `[3,0]` (2 bytes of payload). Gate **G27e** round-trips a
synthetic 980-player / all-tier / 8-season save and asserts `< 64 KB`, with a
hard alarm at 96 KB.

### 3.2 The extension: an identity-at-default multiplier overlay

`simulate` computes `S[side].T` once at kickoff (`teamNumbers`) and reads
`T.create` (via `T.creation`/`shareA`), `T.convert`, `T.prevent` (via
`T.defenceQ`) inside the loop. The overlay scales those three channels and
nothing else.

```js
/* per side, live: identity 1/1/1 unless a verb is active */
S[side].M = { create: 1, convert: 1, prevent: 1 };

function liveCreation(side){ return S[side].T.creation * S[side].M.create; }
function liveConvert(side) { return S[side].T.convert  * S[side].M.convert; }
function livePrevent(side) { return S[side].T.defenceQ * S[side].M.prevent; }

function applyMod(side, mod) {            // consumes ZERO rng
  if (!mod) return;
  const M = S[side].M, CL = (v) => clamp(v, 0.85, 1.15);
  M.create  = clamp(M.create  * CL(mod.create  || 1), 0.78, 1.28);
  M.convert = clamp(M.convert * CL(mod.convert || 1), 0.82, 1.22);
  M.prevent = clamp(M.prevent * CL(mod.prevent || 1), 0.80, 1.26);
  refreshShare();                          // shareA re-derived, no rng
}
function refreshShare() {
  const a = Math.pow(liveCreation(0), 1.3), b = Math.pow(liveCreation(1), 1.3);
  shareA = a / (a + b);
}
```

Consumption sites changed (four, exhaustively):

| site | was | becomes |
|---|---|---|
| `shareA` init | `T.creation` | `refreshShare()` at kickoff |
| shot quality `Q` | `... * S[side].T.convert` | `... * liveConvert(side)` |
| defence `Dq` | `S[other].T.defenceQ` | `livePrevent(other)` |
| knock recompute | `teamNumbers(side)` | `teamNumbers(side)` then `refreshShare()` — `M` survives the recompute |

`pMoment` (tempo) and `T.avgEff` are **deliberately not modded**: the number of
chances per match and `rec.meta.avgEff` stay fixed by mentality alone. That
keeps goals inside 2.4–3.4 structurally, and keeps the `giant_kill` / `hustle`
feats meaning "kickoff strength", which is what they have always meant.

**Every mod site consumes zero rng.** The rng order in the loop is untouched,
which is why G14 can pass and why determinism gate 1 still holds.

### 3.3 The segmented generator — how a live half-time call keeps ⏩ parity

The honesty invariant (FM §7.2 #2) is: *one shared settlement; watching never
pays more; the same seed must settle identically in both routes.* A live
decision at 46' would normally break that, because ⏩ has no pause.

Ruling: **both routes stop at the same points.** `simulate` becomes a thin
driver over a generator, so the rng stream is one continuous mulberry32 and
the record depends only on `(seed, decision sequence)` — never on who made the
decisions or how long they took.

```js
function* simulateGen(A, B, opts, rng) {
  ...
  const talk = yield { stop: 'talk',  min: 0,  score: [0,0] };   applyMod(mySide, talk);
  for (min = 1..90) {
    if (min === 46) { emit(46,0,'half_time');
                      const m = yield { stop: 46, min, score: rec.score.slice() };
                      applyMod(mySide, m); }
    if (min === 70) { const m = yield { stop: 70, min, score: rec.score.slice() };
                      applyMod(mySide, m); }
    ... unchanged ...
  }
  ...
  return rec;
}

/* unchanged public contract — drives the generator with the stored plan */
function simulate(A, B, opts, rng) {
  const g = simulateGen(A, B, opts, rng);
  let step = g.next();
  while (!step.done) step = g.next(planDecide(opts.plan, step, opts.mySide));
  return step.value;
}
```

- `planDecide(plan, step, mySide)` is **pure**: `talk` → the tone's mod;
  `46`/`70` → `plan[lead|level|trail]` chosen by the live score. With
  `opts.plan` absent it returns `null` at every stop ⇒ identity ⇒ **G14**.
- Harness, CPU fixtures, `seededSim`, friendlies and Draft Duel all keep
  calling `simulate()` and are untouched.
- PLAY mode and ⏩ mode both drive `simulateGen` from the UI and both show the
  same half-time card. `p.settings.autoCalls === true` makes the UI answer
  from the plan without a card — the true one-tap holiday.
- **The abandon rule is unchanged**: PLAY may abandon (nothing recorded,
  `attempt++`); ⏩ commits at the first whistle and its stops fast-forward
  but never un-commit. A stop is a *steer*, not a *peek* — the manager sees
  only the score, exactly what a real manager sees at half-time.
- New record field, display-only, alongside `xg`:
  `rec.calls = [{min, which:'talk'|'lead'|'level'|'trail', id, mod}]`.

### 3.4 The three verbs

**Team talk** (fires before minute 1, first half only in feel — it is a single
kickoff mod; the 46' call replaces the manager's voice):

| tone | when it lands | mod (create / convert / prevent) |
|---|---|---|
| `FIRE THEM UP` | squad `moodScore ≤ −0.2` **or** opponent kickoff avgEff ≥ yours | 1.08 / 1.05 / 0.99 |
| | otherwise (already flying) | 0.97 / 0.98 / 0.97 |
| `STEADY` | always | 1.02 / 1.01 / 1.02 |
| `NO PRESSURE` | squad `moodScore ≥ +0.2` **or** you are the favourite | 1.03 / 1.02 / 1.06 |
| | otherwise | 0.99 / 0.99 / 1.00 |

`moodScore = mean over the XI of (form + (energy<60 ? −1 : 0) + (bs≥3 ? −1 : 0))`.
`STEADY` can never be negative — a seven-year-old cannot lose a match on the
team talk. The table is printed behind a `?` chip on TACTICS: the effect is
deterministic and the **feedback is the drama**, not the hiding
("The dressing room roars. +8% attack.").

**In-match calls** (46' and 70', selected by live score against the plan):

| call | create | convert | prevent |
|---|---|---|---|
| `PUSH FORWARD` | 1.12 | 1.05 | 0.92 |
| `HOLD` | 1.00 | 1.00 | 1.00 |
| `SHUT UP SHOP` | 0.88 | 0.97 | 1.12 |

`HOLD` is exact identity — the default plan after migration is
`{lead:'hold', level:'hold', trail:'hold'}`, so **a migrated v2 career plays
byte-identically to how it played yesterday** until the owner changes
something. That is not a nicety; it is what makes G14 meaningful for real
saves.

**Rivalry memory** (`p.rivals[clubId] ∈ 0..3`, applied to the CPU side at
kickoff, before minute 1):

```
after a competitive match vs club C:
  margin = gf − ga
  g = p.rivals[C] || 0
  if (margin >= 3)  g = min(g + 2, 3)        // "they have not forgotten the 5–0"
  else if (margin >= 1) g = min(g + 1, 3)
  else if (margin <= -1) g = max(g - 1, 0)   // beating you settles them
  p.rivals[C] = g                             // pruned at 0
grudge mod on the CPU side = { create: 1 + 0.04g, convert: 1 + 0.02g,
                               prevent: 1 + 0.03g }      // max 1.12/1.06/1.09
```

Surfaces as an `ANGRY ×g` chip on TACTICS, a scout line, and a news card
("Algeria remember the 5–0. Expect a game."). It is **honest**: the chip is
shown before kickoff, so the manager can counter-pick.

## 4. THE RPG CORE (Addendum 15) + THE DUAL GATE (Addendum 14)

### 4.1 XP formula

Awarded inside `settleMatch` only — so **friendlies and Draft Duel award zero
XP by construction** (they never call it), which preserves "friendlies touch
NOTHING else".

```
For each pid with rec.ratings[pid] != null AND p.collection[pid]:
  base    = started ? 60 : cameOn ? 30 : 0
  rating  = clamp(round((rec.ratings[pid] − 6.0) × 20), 0, 80)
  goals   = 25 × (count of pid in rec.scorers[mySide])
  sheet   = (ga === 0 && role(pid) ∈ {GK, DEF}) ? 30 : 0
  motm    = (rec.motm === pid) ? 40 : 0
  win     = won ? 15 : 0
  quest   = quest step completion bonus (§4.4), 0 or 100–500
  raw     = min(base + rating + goals + sheet + motm + win, 250) + quest
  gain    = round(raw × (1 + 0.10 × coachesBoosting('climb'))
                      × (1 + 0.05 × (p.mastery[pid] || 0)))
  p.xp[pid] += gain
Unused bench (in p.lineup.bench, no rating row): +8 flat, no multipliers.
```

Median started-and-fine match ≈ **60 + 20 + 15 = 95 XP**. One match ≈ 100 XP.
That is the whole mental model, and it is printed on the card sheet.

### 4.2 XP gates = the apps gates, ×100

```
XP_GATE (cumulative, to reach tier) = { 1:200, 2:500, 3:900, 4:1400, 5:2000, 6:2800 }
   ( = APP_GATES {1:2, 2:5, 3:9, 4:14, 5:20, 6:28} × XP_PER_APP 100 )
```

**The dual gate** (`trainInfo` gains a second clause; `doTrain` re-checks
both):

```
canClimb(p, pid, fromTier) =
      p.coins >= cost(fromTier) × (1 − (p.disc[pid]||0)) × (1 − 0.05 × mastery)
  AND (p.xp[pid] || 0) >= XP_GATE[fromTier + 1]
  AND (fromTier + 1 < 6 || p.blackLicence)
```

`apps` stays in the save and stays on screen ("played 14") because it is the
kid-legible twin of the bar — but **the gate is XP**, because XP rewards
*playing well*, which is the RPG promise. Both numbers move together for an
ordinary manager; XP moves faster for a good one. Disabled-reason copy:

- `"needs 260 more XP — play him"`
- `"needs 90 more 🪙"`
- `"needs 260 XP and 90 🪙"`
- `"Win the Gibson Cup twice to earn the Black Licence."`
- `"BLACK is the top!"`

### 4.3 Levels are the colours

Tier names ship in `MG_DATA.parallels[i].level` (generator change, one field):

```
white NOVICE · blue PROSPECT · red STARTER · orange KEY PLAYER
purple STAR · green ELITE · black LEGEND
```

Shown on every card face under the tier pips, on the ladder strip, and in the
level-up ceremony. This is the line that teaches the whole game in one glance.

**Level-up ceremony** extends the existing 1.6s training ceremony (`drawCeremony`):
frame transmutes through the colour (already there), plus a light burst, the
new level word stamping in, an eff roll, `env.sfx.fanfare()`, and — new — a
queued inbox one-shot: *"ELLIS ASCENDS — now a STARTER (red). The Sticker
Times approves."* Queued into the next NEWS DAY, never blocking.

### 4.4 Per-card quests

`MG_DATA.quests` (generated): one 3-step chain per position archetype
(GK / DEF / MID / ATT / SPE-crest) plus a hand-authored chain for each of the
nine cast cards. `p.quests[pid] = [step, progress]`, evaluated in
`settleMatch` from the record — pure, no rng.

```
ATT   1) score 3 with him            → +250 XP
      2) score in 3 different matches → 15% off his next climb (p.disc)
      3) score a hat-trick with him   → +500 XP and +1 mastery star
GK    1) 3 clean sheets · 2) a shutout with 10+ shots faced · 3) 5-match CS streak
DEF   1) 5 starts · 2) 3 clean sheets · 3) win a match rated 8.0+
MID   1) 10 starts · 2) MOTM once · 3) MOTM three times
```

Reward types are limited to `xp | disc | mastery | coins`. **No quest ever
grants a free tier** — the dual gate is the point of the addendum. A chain
pays exactly once; **G-flow F7** proves idempotence across a reload.

### 4.5 Mastery stars

`p.mastery[pid] ∈ 0..3`. Earned: 10 career goals with him · a Cup or division
title won with him starting the final · a completed quest chain.

Effect, deliberately economy-only: **+5% XP per star** and **−5% climb cost
per star**, plus a gold star row on the card frame and a swapped commentary
bank. Mastery is forbidden from touching `effSkill` — **G26**. Engine-effect
badges belong to Addendum 17, where the attribute system can carry them
properly; shipping them here would mean inventing per-player engine branches
twice.

### 4.6 The weekly training plan (Addendum 14) and coaches

`p.plan = [slot, slot, slot]`, each `{focus, pid}` or `null`. Resolved once
per completed round, inside the atomic round settle, **after** `settleMatch`:

| focus | effect | cost |
|---|---|---|
| `CLIMB` | `+120 XP` to the card | 25 🪙 |
| `FITNESS` | `+25 energy` (cap 100) — on top of the ordinary rest | 25 🪙 |
| `SHARP` | one step toward `form = +1` (never past +1) | 25 🪙 |
| `SOLID` | GK/DEF only: one step toward `+1`, plus `+15 XP` | 25 🪙 |

Coaches: `p.coaches ⊆ {climb, fitness, sharp, solid}`, max 3, hired for
`economy.coaches.cost = 600` each from the SQUAD/TRAINING tab. A coach makes
its focus **+50% stronger** and its slot **free**. This is the late-game coin
sink addendum 8 needs: three coaches = 1,800 🪙, roughly a season's earnings,
and it competes directly with a green climb.

`form` never leaves `{−1, 0, +1}` and `energy` never leaves `0..100` — the
existing flow-test invariants keep guarding them, unchanged.

## 5. THE MARKET VERBS (Addenda 12, 13)

### 5.1 Shared guard — `canRelease(p, pid, tier)`

Every outbound path (trade, sale, loan) goes through one guard, generalising
today's `sellCombo` XI check:

```
canRelease = NOT (removing this combo would leave p.lineup unfillable)
           AND NOT (pid is a cast/family card the CPU asked for)
           AND NOT (pid is currently on loan out)
           AND p.collection[pid] owns tier
```
"Unfillable" is tested by actually running `autoFill` on a clone and checking
9 legal slots + exactly one GK + `maxBlackInXI ≤ 1`. Fuzzed by **G23**.

### 5.2 Trades (Addendum 12)

Club personality already exists as `TAUNT_PERSONA` and `club.tier`; add a
generated `club.persona ∈ {lowball, cheeky, fair, generous}` to `MG_DATA`
(Uruguay → `lowball` — "I play fair. Mostly."; Argentina → `cheeky`; tier-1
minnows → `generous`; the rest → `fair`).

**CPU-proposed** (generated at each window and at round boundaries, seeded —
`h = (season.seed ^ round×7919 ^ 0x7AD)`):

```
want   = one of YOUR fieldable, releasable combos, weighted by
         (their squad's need at that role) × (your card's value) × (form + 2)
give   = a combo from their squad, chosen so that
         theirValue ≈ yourValue × personaRatio
           lowball 0.72 · cheeky 0.85 (but one tier higher than expected)
           fair 1.00 ±0.05 · generous 1.12
offer  = { kind:'trade', club, want:[pid,tier], give:[pid,tier],
           delta: theirValue − yourValue, expires: round + 2 }
```

Rendered as an inbox decision card with the delta shown plainly
(`+180 🪙 in your favour` / `−240 🪙 against you`) and the two cards drawn side
by side by the existing card renderer. One tap: `SWAP` / `NO THANKS`.
Never a timer; expiry is a silent removal plus one kind line.

**Player-proposed** (MARKET → TRADE tab): pick one of yours, pick a target
from a **scouted** club's squad (`isScouted` already exists and already earns
its keep via crest cards), press PROPOSE. Acceptance:

```
gain     = theirGetValue − theirGiveValue                     // from their side
p_accept = clamp(0.50 + 0.90 × gain / max(yourValue, theirValue)
                      + personaBias                          // −0.10..+0.10
                      + 0.06 × form(offeredCard)
                      − 0.10 × (p.rivals[club] || 0), 0.02, 0.95)
roll     = mulberry32( season.seed ^ round×2654435761 ^ hash(want+give) )()
```

The seed is a function of **the exact proposal**, so re-proposing the same
swap gives the same answer — no save-scum, no retry-until-yes. Change the
offer, get a fresh roll. **G22b** proves it.

**Hot-seat trades** (p1 ↔ p2): the existing `PASS TO <NAME> 👐` interstitial
pattern from FRIENDLY, twice. Both profiles confirm; the swap executes
atomically; both profiles are written in one `saveNow()`.

Trades move `(player, tier)` combos exactly — `removeCombo` / `addCombo` — so
trading *for a higher tier of a card you love* is a real progression route,
which is the addendum's stated intent. `apps`, `xp`, `mastery` and `quests`
belong to the **player id**, so a card traded away and reacquired keeps its
history; a card acquired at a new tier inherits the player's meters. That is
correct: the sticker changed, the footballer did not.

### 5.3 Loans (Addendum 13)

`p.loans = [{ pid, tier, club, from, until, fee, apps, rsum }]`, max 3 active.

- **Send**: one tap from SQUAD list or the card sheet → confirm. Requires
  `canRelease`. Fee paid immediately: `round(value × 0.12)`; plus
  `round(value × 0.04)` per round the spell runs, paid at return.
- **While out**: the card stays in `collection` but is excluded from
  `autoFill`, the slot picker, trades and sales; the binder shows it dimmed
  with `ON LOAN AT ALG`. Guard lives in `isAvailable(p, pid)` — one predicate,
  used everywhere.
- **The spell is derived, never stored beyond `[apps, rsum]`.** The loan club's
  fixtures already sim deterministically (`seededSim`); the loan rating for a
  round is read from that club's record (`rec.ratings[pid]` when the stitched
  card starts, else a seeded 6.2–7.6 draw from
  `mulberry32(season.seed ^ round ^ hash(pid))`). Zero extra cost, fully
  re-derivable. **G24**.
- **Return** at season review: `apps += spellApps`,
  `xp += spellApps × 90`, `form = +1` if `avgR ≥ 7.0` else unchanged,
  a `dynasty.loans` entry, and an inbox card
  ("Ellis is back from Algeria — 11 games, 7.3 average. He looks taller.").
- **Recall costs a window**: allowed only while `windowOpen(p)`
  (`season.results.length === 0`), matching the existing transfer window.
  Outside it the button reads `recall in the next window` — a real cost, no
  penalty.

This is explicitly the development route for benched family cards, which is
what the owner asked for: Gibson and Ellis can be loaned **out by you**, and
are never asked for by anyone.

### 5.4 Selling upward (Addendum 13)

Extends the shipped `makeOffers`, which currently picks a random club and a
flat 1.15× multiplier. New generator:

```
bidders = clubs whose division index < p.division      // strictly above you
for a player with form >= 0 and (avgRating >= 6.8 or vd >= 1):
  bid = round( valueOf(pid, tier, vd)
             × (1 + 0.12·form + 0.03·clamp(avgRating − 6.5, 0, 3))
             × (1.05 + 0.10 × (p.division − bidderDivision)) )
offer = { kind:'sale', pid, tier, club, coins: bid, expires: round + 2 }
```

Two divisions up on a hot striker ≈ **1.25 × 1.3 ≈ 1.6× book value** — the
drama of a big club circling a favourite, in one honest number.

- **Accept** → coins in, combo out (via `canRelease`), a `dynasty.sales`
  record, an inbox follow-up ("He waves from the tunnel. Good luck, son.").
- **Reject** → `p.bs[pid] += 2` (the existing sulk channel, already bounded and
  already gated) and one line. **No form penalty beyond the sulk driver**, so
  `form ∈ {−1,0,+1}` still holds. No board, no ultimatum, no repeat nagging:
  a rejected bidder does not return that season.
- **Player-initiated**: `OFFER UPWARD` on the card sheet → seeded response
  next round: a bid, or a kind refusal with a real reason
  ("Portugal like him. They want to see a run of games first.").

### 5.5 Anti-exploit posture

Trades and sales are the only places in this game where value can be
manufactured. Three structural brakes, all gated by **G22**:

1. Acceptance rolls are seeded on the proposal, not the attempt.
2. Offers are generated at most twice per round and expire.
3. **G22a**: over a scripted 5-season career that trades greedily and
   optimally, total portfolio value may not grow more than **15% per season**
   above the same career that never trades. If it does, `personaRatio` and the
   division multiplier are re-tuned before merge.

## 7. BROADCAST DEPTH (Addendum 14) — presentation only

All of this lives in `drawMatch` and new helpers; none of it reads or writes
game state, so it cannot move a gate. Project law holds: **procedural only, no
image assets, no CDN.**

- `drawStadium(ctx, ctxState)` — four parallax layers behind the pitch: far
  stand silhouette, near stand with a **deterministic crowd dot-field seeded
  from the club id** (so a club's crowd looks like itself every time), tier
  rails, floodlight cones with bloom.
- `crowdEnergy ∈ 0..1` from `mm.momentum`, chance sequences and goals; ripple
  = a travelling sine phase across the dot field; eruption = vertical jitter +
  `env.shake(px)` (which already swells the framework's crowd bed via
  `Music.swell`) + a 0.4s bloom.
- **Day / dusk / night** from `(seed ^ round) % 3` — sky gradient, light
  bloom alpha, shadow direction. Free, deterministic, zero save cost.
- **Weather**: knockout ties only, `(seed ^ round) % 4 === 0` ⇒ rain streaks +
  wet-pitch specular on the mow stripes.
- **Camera punch-in**: `mm.cam = {k, cx, cy, t}` around the pitch draw only
  (chrome never scales), ease-out 0.9s on goals and penalties.
- **Replay flash**: the goal's `mm.seq.steps` are already stored — re-run them
  as a ghost ball trail in the scoring club's colour, 0.8s, once.
- **Club colour theming**: `themed(SL, p.colors)` recolours panel edges,
  header rule, chip fills and the CONTINUE button. Focus ring, honesty
  footer, and W/D/L status colours are exempt.
- **`p.settings.reduceMotion`** disables punch-in, shake and the ripple —
  torture-dossier hygiene, and it is a real accessibility answer.

**Performance is a gate, not a hope.** Add a dev-only rolling frame-time
counter (`window.__MG_PERF = {p50, p95}`, one push per `update`). Tap script
`broadcast-look.json` on the **iphone** profile asserts `p95 < 20 ms` across a
full watched match. If the stadium costs more than that, layers get baked to
an offscreen canvas once per match rather than being redrawn per frame.

## 10. RISKS, AND WHAT IS DELIBERATELY NOT IN THIS CYCLE

**Risks, ranked.**

1. **The engine edit.** Mitigated entirely by capturing G14's golden fixture in
   Phase 0, before a single character changes. If the fixture is not captured
   first, this plan has no safety net and Phase 2 must not start.
2. **Save size.** `quests` is the only unbounded new map; it is capped by
   storing only started chains and collapsing completed ones. G27e watches it.
3. **Economy drift.** Three new sinks (coaches, plan slots) and two new taps
   (trades, sales) land in the same cycle. G25 re-runs the pacing gate at the
   end of Phase 9, and again in Phase 11. Expect one re-tune of `personaRatio`
   and the division multiplier; budget for it.
4. **Frame budget on the phone.** The stadium is the only thing in this plan
   that can cost frames. It ships last, behind a p95 gate, with a bake-to-
   offscreen fallback already designed.
5. **Copy drift into nag territory.** Offers, bids and expiry are exactly where
   a money game's habits creep in. The §0 rules are the review checklist:
   no timers, no urgency colour, no repeat asking, expiry is silent.

**Not in this cycle, and why:**

- **Live free-form half-time substitutions.** The generator supports a stop at
  46'; substitutions would also need a lineup edit mid-record, which touches
  `S[side].pitch` and the auto-sub path. It is a clean v4 item on top of
  `simulateGen`, and this plan deliberately leaves the seam open for it.
- **Engine-effective badges/traits (Addendum 17.3).** They need the ~29
  sub-attribute set to be principled. Mastery here is economy-only so that
  Addendum 17 can add engine effects **once**, properly, instead of twice.
- **Save slots (Addendum 17.1).** Not built, but `SLOT_KEY()` is introduced in
  Phase 1 so the slot work is a one-line change plus a screen, and the v2→v3
  chain already makes "the existing save migrates into slot 1" trivial.
- **Attributes, potential, age and synergy panels (Addenda 17.2, 18).** Not in
  this cycle — but the card sheet rebuilt in Phase 3 **is** Addendum 18's
  screen in embryo: it already ships that addendum's first bullet (portrait,
  nation, position, parallel, 75/25 eff, **XP bar, mastery stars**) and its
  career-totals row (apps, goals, avg rating, value drift). Build it with a
  **tabbed shell** — `PROFILE | LADDER | QUESTS` — so 17/18 add
  `ATTRIBUTES` and `SYNERGY` tabs rather than redesigning it. Two forward
  hooks to leave in place while it is cheap: reserve
  `MG_DATA.synergyIndex` (a precomputed per-player partner index — Addendum
  18 forbids a per-frame 980×980 scan) and keep every number on the sheet
  derived from a named function, never inlined, so the attribute layer can
  replace a derivation without touching layout.
- **Team-talk imperfect information.** FM hides it; we show the table. For a
  seven-year-old the drama is the *feedback*, not the fog. Revisit only if the
  owner asks.
